# 博客三套独立前端完全重构设计

日期：2026-07-29

状态：用户已于 2026-07-29 批准，进入实施阶段

适用仓库：`MingToneFurry/blog`

## 1. 背景

仓库当前为 Astro 静态博客，内容来自 Astro Content Collections，页面与组件主要沿用 Fuwari 的布局和组件树。Umami 分享 API helper 已经修复并合入 `main`，所有 helper 请求均使用 `startAt=0`，表示 Umami 开始记录以来的累计值；但现有 Fuwari 组件仍有重复内联统计脚本、`0` 初始占位和局部仅渲染 PV 等历史实现，三套完全重构必须统一迁移这些 DOM 消费端，而不是只复用 helper 即视为完成。

仓库包含三份受 Git 跟踪的设计规范：

- `iudesigns/arcade.md`
- `iudesigns/glass.md`
- `iudesigns/mono.md`

现有 `design/arcade`、`design/glass`、`design/mono` 分支已经完成一轮视觉重写，但仍大量复用原来的 `Layout`、导航、侧栏、文章卡和页面骨架，属于深度换肤而非完整产品重构。用户已明确要求进一步发散，并批准将三套方案重做为三个独立产品。

## 2. 目标

1. 保留 Astro、Markdown 内容集合、静态构建和现有部署链。
2. 只共享无视觉的数据与行为契约，不共享页面骨架或视觉组件。
3. 将 ARCADE、GLASS、MONO 分别实现为独立的信息架构、导航模型、组件树、阅读体验和移动端交互。
4. 保持所有现有公开 URL、中文文章 slug、分页、RSS、Sitemap 和外链行为兼容。
5. 保留现有主要功能、页面分类、动态背景接口及 Umami 累计统计。
6. 三套重构分别保存在独立设计分支，用户选定前禁止合入 `main`。
7. 每套方案在交付选择前必须有完整的桌面、移动端、功能、无障碍和失败降级证据。

## 3. 非目标

- 不更换 Astro，也不迁移到 React、Vue、Next.js 等其他框架。
- 不重写 Markdown 内容或改变文章正文语义。
- 不改变公开路由，不通过重构制造 SEO 迁移工作。
- 不要求三套产品共享视觉组件或保持相同 DOM。
- 不把动画数量、复杂框架或客户端状态管理当作重构质量指标。
- 不修改 Umami 账户权限、分享设置或动态令牌机制。
- 用户选择风格前，不将任何设计实现合入 `main`。

## 4. 已批准的产品决策

### 4.1 独立程度

采用“独立产品”方案：三套产品只共享内容 schema、路由契约、类型和纯逻辑。以下内容不得为了复用而共享：

- 页面 Shell 与 Layout
- Navbar、Sidebar、Footer 的视觉组件
- 首页文章模块与文章卡
- 文章 Reader 与 TOC 呈现
- 移动菜单、Dialog、Drawer、命令面板
- CSS token、布局 CSS、视觉状态与动效实现

共享层不得包含 `className`、切角、圆角、布局列数或风格名称等视觉信息。

### 4.2 三套产品定位

- ARCADE：高互动的探索型任务控制台。
- GLASS：中等互动的个人数字观测站与内容中枢。
- MONO：极简交互、阅读优先的数字出版物。

三套产品可以使用不同的置顶、分组和推荐逻辑，但所有文章始终可以通过首页分页、归档或搜索访问。

### 4.3 导航与功能

全部现有路由和分类保留，但每套产品可以重新编排入口，例如任务导航、分组中枢、刊物索引或命令面板。核心功能三套齐全，同时允许增加不改变内容兼容性的风格专属体验。

### 4.4 动态背景

以下接口与设置为不可破坏契约：

- 主接口：`https://api.furry.ist/furry-img`
- 回退接口：`https://sni-api.furry.ist/furry-img`
- 保留背景显示/隐藏和模糊设置

同一图片源在三套产品中承担不同角色：

- ARCADE：任务场景和视觉冲击源。
- GLASS：克制的观景窗或编辑场景。
- MONO：灰度刊物封面或页边图，不作为持续干扰正文的壁纸。

### 4.5 技术基础与兼容

- 保留 Astro Content Collections、Markdown、静态路由和部署配置。
- 所有现有 URL、文章 slug、RSS、Sitemap、分页和外链保持。
- 客户端能力采用渐进增强：关闭 JavaScript 时仍能阅读正文、浏览导航和访问分页。

## 5. 分支与 Git 架构

### 5.1 `main`

`main` 在用户选择前仅保留：

- 已完成的 Umami 修复
- 设计规范与交接文档
- 与设计实现无关的必要仓库维护

内容 schema 扩展、共享 headless 模块和任何三套前端实现均不得提前合入 `main`。

### 5.2 设计基础分支

从 `main` 创建未合并的 `design/rebuild-core`，仅承载三套设计都需要的无视觉改动：

- 可选内容元数据 schema
- 内容查询、排序和归类纯函数
- 路由、日期、阅读时间和 URL 纯函数
- 统一的累计统计访问层
- 动态背景加载与回退状态机
- 设置持久化和无视觉生命周期工具
- 共享契约类型与契约测试

该分支不得包含页面 Layout、视觉组件或风格 CSS，也不得在用户选择前合入 `main`。

### 5.3 风格分支

现有分支继续作为最终交付分支：

- `design/arcade`
- `design/glass`
- `design/mono`

每个分支合入 `design/rebuild-core` 后，在已有第一轮视觉提交之上完成架构级替换。旧提交保留为 Git 回退点，不 reset、不改写历史。

每个阶段均更新对应 `HANDOFF.md`，提交后推送远端。用户选定风格前，三者均禁止合入 `main`。

## 6. 共享 Headless Core

### 6.1 内容契约

在保持现有字段兼容的基础上增加以下可选字段：

- `category?: string`
- `series?: string`
- `type?: string`
- `featured?: boolean | number`

缺省规则：

- 没有 `category` 时归入稳定的默认分类。
- 没有 `series` 时不进入系列导航。
- 没有 `type` 时按普通文章处理。
- 没有 `featured` 时权重为零。
- 现有 `pinned` 继续有效，并优先于普通文章。

不得要求一次性手工改完所有旧文章。现有 frontmatter 即使缺少新字段也必须通过 schema 和生产构建。

### 6.2 统一数据接口

共享层向风格层提供纯数据，不提供 DOM：

- `PostSummary`
- `PostNavigation`
- `PostCollectionGroup`
- `LifetimeStats`
- `NavigationItem`
- `FriendRecord`
- `BackgroundState`
- `AppearanceSettings`

共享查询负责：

- 过滤 draft
- pinned、featured 和发布时间的稳定排序
- 分页
- 分类、系列和类型的缺省处理
- 上一篇/下一篇
- 阅读时间与字数
- URL 规范化和中文 pathname 解码

### 6.3 生命周期

无视觉生命周期模块提供幂等入口，支持首次加载和 Swup 页面替换。每个增强模块必须满足：

- 同一页面重复初始化不会重复绑定监听器。
- 页面离开后可清理临时监听器和动画。
- 页面切换后只扫描当前 DOM 中尚未完成的目标。
- 单个增强失败不会阻塞其他增强或基础导航。

## 7. ARCADE：Field Node

### 7.1 信息架构

首页是任务控制台，而非侧栏加文章卡列表：

1. 顶部系统条显示站点身份、累计 PV/UV、搜索和显示设置。
2. 主视觉使用动态背景作为“当前场景”。
3. pinned/featured 内容作为 Active Mission。
4. 最新文章作为 Transmissions，可按 type/category 显示任务标签。
5. 归档、友链、状态、关于等成为可进入的系统模块。
6. 桌面使用紧凑的左侧任务轨；移动端使用底部模块 Dock 与全屏命令面板。

### 7.2 阅读体验

- 文章头为任务简报，包含标题、摘要、日期、字数、阅读时间和累计 PV/UV。
- 正文采用高可读单列，HUD 只存在于边缘，不侵入 Markdown 内容。
- 阅读进度使用分段任务轨。
- TOC、搜索和页面跳转可以从命令面板呼出。
- 专属增强：键盘导航、命令面板、任务完成式阅读反馈。

### 7.3 视觉与动效

严格遵循 `iudesigns/arcade.md`：无圆角、分级切角、唯一电光黄、硬 offset 阴影、编号和斜线装饰。允许冲击型短动效，但单次主要动效不超过规范时长；`prefers-reduced-motion` 下移除 skew、overshoot 和大位移。

## 8. GLASS：Observatory

### 8.1 信息架构

首页是个人数字观测站：

1. 顶部 compact bar 提供身份、分组导航、搜索和显示设置。
2. 动态背景被限制在观景窗或编辑场景，不成为整页磨砂壁纸。
3. 首屏并列显示站点介绍和累计 PV/UV。
4. 最新写作、分类集合、个人资料、友链与运行状态组成有层级的观测模块。
5. 页面入口按 Writing、Identity、Network、System 分组。
6. 移动端使用顶部 compact bar 和上下文工具抽屉。

### 8.2 阅读体验

- 正文位于安静的编辑工作台中央。
- 桌面右侧上下文 rail 容纳 TOC、累计统计、分类/系列和上一篇/下一篇。
- 移动端将上下文 rail 折叠为文章工具抽屉。
- 专属增强：内容概览、分类筛选、观测数据模块。

### 8.3 视觉与动效

严格遵循 `iudesigns/glass.md`：单一强调蓝、发丝描边、有限圆角、卡片无常规外投影、点阵画布和克制动效。名称虽为 GLASS，但不得退化为全站磨砂玻璃堆叠。

## 9. MONO：Journal

### 9.1 信息架构

首页是一份数字刊物：

1. Masthead 显示站名、卷期、主索引和 RSS。
2. pinned/featured 内容作为刊首文章。
3. 其余文章使用顺序编号的编辑索引，而非卡片网格。
4. 分类、系列、归档和搜索构成出版物索引。
5. 个人信息、友链、状态和累计统计退居 masthead、页边或尾注，但仍可直接访问。
6. 移动端保持单线性刊物结构，不引入卡片横滑或复杂抽屉。

### 9.2 阅读体验

- 窄正文、宽留白、排版优先。
- TOC、累计 PV/UV、发布日期和阅读时间以边注或脚注表达。
- 专属增强限于阅读模式、键盘前后篇和简洁的索引跳转。
- 动态背景图只作为灰度刊物封面或页边图；正文区域保持纯色。

### 9.3 视觉与动效

严格遵循 `iudesigns/mono.md`：黑白灰、全直角、1px 边框、无渐变、无模糊、无纹理、无装饰投影。动效只用于状态说明，位移和时长保持规范上限。

## 10. 核心功能保留矩阵

以下能力在三套产品中必须全部存在，但入口和视觉可以不同：

- 首页 4 页分页与全部文章访问
- 文章日期、更新时间、描述、封面、标签/分类、字数、阅读时间
- 全站及单篇文章累计 PV/UV
- 归档
- RSS 文章搜索
- 关于、联系方式、隐私
- 动态 JSON 友链
- 外部状态页与 Umami 统计页
- 明暗/系统主题
- 动态背景显示/隐藏与模糊
- Swup 页面切换
- Markdown、代码块、图片回退、外链卡片和 GitHub 卡片
- TOC、上一篇/下一篇、返回顶部
- License、GitHub 编辑链接
- Footer、RSS、Sitemap、robots.txt、404
- 个人资料和社交链接

当前友链记录来自 `src/data/friends/*.json`，由 `import.meta.glob(..., { eager: true })` 在构建期汇总进静态 HTML。本文中的“动态 JSON 友链”指多 JSON 文件驱动、无需在页面组件中硬编码卡片，而非浏览器运行时远程拉取。完全重构继续保留这一构建期协议；不新增远程友链 API、缓存层或客户端数据同步。

允许的专属增强不得改变以上能力的可访问性，也不得要求客户端 JavaScript 才能阅读正文或访问路由。

## 11. Umami 累计统计

### 11.1 统计口径

- 全站与单篇文章均固定使用 `startAt=0`。
- UI 明确写“累计浏览 PV / 累计访客 UV”或等价语义。
- 接入 Umami 前或已删除的数据无法补算，不得声称为域名诞生以来的绝对总数。

### 11.2 加载规则

- 初始值为 `--`，不得先伪装为 `0`。
- 只有 API 明确返回真实零时才显示 `0`。
- 分享令牌运行时动态获取，不写入仓库、构建产物中的固定配置或 HANDOFF。
- 文章 path 过滤必须规范化并支持中文 slug。
- 首页文章统计使用有限并发和有限重试，避免串行超时与网关限流。
- 三套风格只替换数值节点，不依赖统计脚本重建整块 UI。
- `design/rebuild-core` 只负责提供唯一的累计统计访问层、无视觉 DOM 属性协议和契约测试，不修改 `Profile.astro`、`PostMeta.astro`、`PostCard.astro` 或文章页视觉组件。
- 三个风格分支分别删除其页面继承到的旧内联统计逻辑，并将自己的全站、文章列表和详情节点接入 core 协议；不得让旧脚本和新脚本同时请求或竞争写入。
- 统一契约同时覆盖全站 PV/UV、首页每篇 PV/UV、文章详情 PV/UV。首页文章卡和详情页不得只实现 PV。
- core 协议和契约测试规定所有统计节点的未完成态必须为 `--`；实际消费端从历史 `0` 迁移到 `--` 的 DOM 改动由三个风格分支分别完成，而非 core 分支修改视觉组件。

### 11.3 失败行为

- 令牌、网关、网络或单篇请求失败时保持 `--`。
- 可进行有限退避重试，但不无限轮询。
- 单篇失败不影响其他文章统计。
- Swup 替换后重新扫描未完成节点，已成功节点不重复请求。

## 12. 动态背景状态机

1. 页面先以符合当前风格的纯色画布可用。
2. 若用户关闭背景，不发起不必要的图片呈现工作。
3. 启用背景时请求主接口。
4. 主接口失败后切换 SNI 回退。
5. 两者均失败时保留纯色画布，不显示破图或无限 loading。
6. 模糊和显示设置持久化，并在 hydration 前尽早应用，减少闪烁。
7. 每套产品只负责图片的裁切、灰度、对比与放置，不更换来源契约。

## 13. 搜索、主题与页面切换

### 13.1 搜索

保留 RSS 搜索的数据来源与可访问语义。可按产品呈现为命令面板、搜索弹层或出版物索引。加载失败时必须可以关闭，不阻塞页面导航。

### 13.2 主题与设置

三套均支持浅色、深色和跟随系统。每套拥有自己的 token，但共用无视觉设置键和存储读取逻辑。主题必须在首屏尽早确定，避免明显闪烁。

### 13.3 Swup

保留现有无刷新导航能力，但不要求三套产品复用当前 `MainGridLayout`。现有配置将容器固定为 `main` 和 `#toc`，因此实施计划必须为每个风格明确选择并测试以下一种方案：

1. 保留语义 `main` 作为主内容交换容器，并在每个路由稳定输出 `#toc`（可为空），视觉结构仍可完全不同；或
2. 在该风格分支调整 Swup containers，并保证所有路由输出一致的新容器集合。

不得出现某些页面缺少配置容器而导致切换失败。所有页面增强必须同时通过直达 URL 与 Swup 切换验证。若某专属交互与 Swup 冲突，应简化该交互，不得牺牲导航可靠性。

## 14. 无障碍、响应式与性能

### 14.1 无障碍

- 使用语义 header、nav、main、article、aside、footer。
- 所有交互可键盘完成，并有清晰可见的 focus 状态。
- 触控目标不小于 44px。
- 颜色对比达到 WCAG AA。
- Dialog、Drawer、命令面板具有正确命名、焦点进入/返回和 Escape 关闭行为。
- 动态统计具有不会打断阅读的更新语义。
- 全部动效支持 `prefers-reduced-motion`。

### 14.2 响应式

- 精确验证 390x844，不得出现页面级横向溢出。
- 桌面和移动端允许使用不同导航模型，不要求简单缩放。
- Markdown 表格、代码块和长 URL 必须在局部容器内安全滚动或换行。
- TOC 和上下文信息在小屏转为抽屉、边注或线性区块，不覆盖正文。

### 14.3 性能

- 静态 HTML 优先，交互按需 hydration。
- 不为纯视觉效果引入大型客户端框架或常驻全局状态。
- 动态背景不得阻塞正文 LCP；背景解码完成前使用纯色占位。
- 控制首屏 CLS，统计从 `--` 更新为数字时预留宽度。
- 避免同一图片和同一统计在单次页面生命周期重复请求。

## 15. 错误处理与渐进增强

- 无 JavaScript：正文、导航、分页、归档和友链内容仍可访问；搜索、主题切换和统计可降级。
- Umami 失败：保持 `--`，不显示虚假数据。
- 背景失败：主接口到 SNI 回退，再到纯色画布。
- 友链数据异常：显示稳定的空状态或跳过坏记录，不破坏整个页面。
- 搜索索引失败：显示可关闭错误状态，保留普通导航和归档入口。
- 图片失败：沿用域名回退与稳定占位。
- 单个专属增强异常：不得阻止页面切换或正文阅读。

## 16. 验收与测试

### 16.1 自动化门槛

每个分支至少运行：

- `pnpm test:umami`
- 共享内容/排序/背景状态机契约测试
- `pnpm build`，必须生成当前完整静态页面集合（基线为 36 页）
- `pnpm type-check`
- `git diff --check`

当前 `type-check` 存在既有 `hast` 类型依赖缺失。实施计划必须先确认并修复或明确隔离该基线；不得把新增类型错误混入同一噪声中。`astro.config.mjs` 当前还存在重复导入 `defineConfig` 的源码冗余，但 2026-07-29 实测 `pnpm build` 仍成功生成 36 页；实施中应清理该冗余并把构建实测作为权威证据，不能仅凭静态观感把它误报为构建阻塞。

### 16.2 浏览器功能矩阵

每个分支分别验证：

- 直达首页、分页 2-4、归档、友链、关于、联系方式、隐私、404
- 直达中文 slug 文章和英文 slug 文章
- 首页 8 篇文章统计与全站统计
- 文章详情累计统计
- 搜索打开、输入、结果跳转、关闭和失败状态
- 主题三态、背景显示/隐藏、模糊持久化
- Swup 首页到文章、文章到归档、前进/后退
- TOC、上一篇/下一篇、返回顶部
- Footer、RSS、Sitemap、License 和 GitHub 编辑链接
- 动态背景主接口、回退和纯色降级

### 16.3 视觉与体验矩阵

- 桌面与精确 390x844 截图
- 无页面级横向溢出
- 键盘完整路径与 focus 可见性
- reduced-motion
- 明暗主题
- 慢网、统计失败、背景失败
- 正文长代码、表格、长链接和图片
- 三套方案之间的信息架构和交互差异清晰可辨

### 16.4 统计可靠性

每套首页至少连续三轮重新加载，每轮等待统一验收窗口，确认所有当前页文章 PV/UV 从 `--` 变为数字；同时验证真实失败时仍保持 `--`。验收脚本或记录必须列出文章数量、成功数量和失败路径，不以只检查第一篇代替整页验证。

## 17. 交付物

每个设计分支交付：

- 完整实现提交与远端分支 SHA
- 更新后的 `HANDOFF.md`
- 桌面与 390x844 首页截图
- 至少一张文章页截图
- 自动化命令结果
- 浏览器功能矩阵结果
- 已知问题与基线问题说明

最终向用户同时展示三套方案。用户选定前保持 `main` 不含设计实现；选定后再制定该分支合入 `main` 的单独计划。

## 18. 完成定义

只有以下条件全部满足，完全重构阶段才算可供选择：

1. 三套产品不共享页面骨架或视觉组件，且结构差异可由代码和浏览器证据证明。
2. 所有核心功能与公开 URL 在三套分支均保留。
3. 动态背景与 Umami 累计统计在三套分支均通过成功和失败路径验证。
4. 自动化构建、契约测试、diff 检查通过；类型检查无新增错误。
5. 桌面、移动端、键盘、动效降级和无溢出验收完成。
6. 三个分支均提交、推送并更新授权环境交接文档。
7. `main` 未包含任何设计实现提交。
